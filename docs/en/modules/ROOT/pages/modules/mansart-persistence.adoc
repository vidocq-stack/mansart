= mansart-persistence
:description: Jakarta Persistence 3.2 (JPA) implementation — restarted, skeleton only; mansart-jakarta-data covers everyday needs.

[.lead]
`mansart-persistence` is Mansart's {spec-jpa-3-2}[Jakarta Persistence 3.2] implementation, under the Maven parent `mansart-jpa`: `EntityManager`, persistence context, JPQL, Criteria API, lifecycle callbacks, the standard metamodel. **Status: restarted, skeleton only** — the module is in the reactor, but nothing in it can be used yet.

[NOTE]
====
For everyday needs in Vidocq (CRUD, typed queries, pagination, `@Transactional`), `mansart-jakarta-data` (delivered) is largely enough. The `vidocq-runtime-mansart-h2-example` example shows a full integration without `mansart-persistence`.
====

== Why a separate module

Jakarta Data 1.0 and Jakarta Persistence 3.2 do not serve the same purpose:

* **Jakarta Data** — typed declarative repositories, stateless, no L1 cache, direct ResultSet mapping. Covers 80% of common application needs. Delivered.
* **Jakarta Persistence** — imperative `EntityManager`, persistence context (managed/detached), L1 cache, listeners (`@PrePersist`, `@PostLoad`), rich JPQL, Criteria API. Required for: complex entity graphs, long transactions with batches of modifications, applications ported from Hibernate that rely on the persistence context.

Both modules render their SQL through the same dialect SPI (`mansart-data-dialect-spi`). No SQL duplication.

== Principles

* **TCK first** — no implementation milestone starts before the official TCK runs (P0); every later milestone is closed by a TCK delta, not by a green build.
* **Zero implementation library** — only `jakarta.persistence-api` (plus the CDI, inject and transaction APIs in the integration module). The JPQL parser is hand-written, XML is read with StAX.
* **No runtime reflection on entities** — entity access, instantiation and metamodel are generated: APT for sources, a Maven plugin for jars, the Class-File API at bootstrap for opaque archives.
* **No proxy or bytecode library, no `ClassTransformer`** — lazy to-one through generated subclasses, lazy collections through Mansart's own wrappers, dirty checking through snapshots.
* **Shared Mansart bricks** — SQL through `mansart-data-dialect-spi` (H2, PostgreSQL), JTA through `mansart-transactions`, any `DataSource` (for instance `mansart-pool`).
* **Virtual threads** — JDBC on virtual threads, no `synchronized` around I/O, `ScopedValue` instead of `ThreadLocal`.
* **Strict Java Modules** — one `module-info.java` per module, the provider published through `provides`, internals not exported.
* **Certification on PostgreSQL** — the database of the official TCK; H2 is for unit tests only.

[#target-modules]
== Target modules

[cols="2,2,4"]
|===
| Module | Java module | Role

| `mansart-jpa-core` | `io.vidocq.mansart.jpa.core` | Bootstrap (`persistence.xml`, `PersistenceConfiguration`), `EntityManagerFactory`, `EntityManager`, persistence context, flush engine, JDBC executor, schema generation; `provides jakarta.persistence.spi.PersistenceProvider`.
| `mansart-jpa-query` | `io.vidocq.mansart.jpa.query` | JPQL lexer and parser, Criteria API, SQL lowering.
| `mansart-jpa-processor` | `io.vidocq.mansart.jpa.processor` | APT: `_Entity` static metamodel, entity accessors and instantiators for application sources.
| `mansart-jpa-maven-plugin` | — | The same generation for entities in dependency jars.
| `mansart-jpa-cdi` | `io.vidocq.mansart.jpa.cdi` | `@PersistenceContext` / `@PersistenceUnit`, JTA-bound contexts.
| `mansart-jpa-tck` | — | Official TCK runner, out of the reactor.
|===

Out of scope: runtime bytecode enhancement, Java agents, dynamic proxies; reactive / R2DBC; multi-tenancy and NoSQL mappings; dialects other than H2 and PostgreSQL until the SPI is stable.

== Meanwhile

For JPA needs in Vidocq today:

* If CRUD + typed queries are enough → `mansart-jakarta-data` (delivered, TCK 74/74).
* If advanced JPQL not covered by JDQL is needed → native SQL via `Connection.prepareStatement(...)` (`@Query` takes JDQL, not SQL).
* If JPA listeners are needed → application-level workaround (CDI interceptors, `@Transactional` + explicit before/after save).
* If a persistence context is needed → wait for `mansart-persistence`.
