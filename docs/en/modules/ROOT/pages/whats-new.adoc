[#rc2]
== Added in 0.4.0-RC2 (since 0.4.0-RC1)

* xref:internals.adoc#generated-code[Generated code and reflective fallback] — one table lists what Mansart generates at build (repository implementations, entity models and metamodels, the per-package `_MansartComponents`, the repository lists), what uses it at run time and what runs when it is missing, followed by when the run-time path still runs and how to tell which path ran.
* xref:reference.adoc#application-modules[Reflection once, not on every call] — a JDQL statement left to the run time finds its repository method once, `@Transactional` caches the annotation per bean class and method, and the CDI extension no longer loads every class of the archive at startup, only the possible repository implementations.
* xref:reference.adoc#application-modules[Entities and repositories without `opens`] — Mansart reaches an application's entities, repositories and projection records without reflection: a generated `_MansartComponents` service per package hands it the entity models and creates the repository implementations, and a projection into a record is built by generated code. A named application module needs no `opens` for them; reflection stays the fallback without the processor or on another container. A one-attribute `SELECT` into a one-component record works (it was read as a plain column).
* xref:reference.adoc#migration-check[A missing table, caught at build time] — when the application ships Flyway SQL migrations, the annotation processor warns about an entity whose table no migration creates, and names the fix: `@Table(name = "book")` when a migration creates `book` for `Book`, whose default table is `books`. `-Amansart.migrationCheck=off` turns it off, `-Amansart.migrations` names other directories.
* xref:reference.adoc#table-names[Table and column names, and a missing table] — the naming rules are documented: a table is named after the entity's class in snake_case and plural (`Book` -> `books`), unlike Jakarta Persistence, and `@Entity(name)` does not change it. A repository whose table does not exist now fails with a message naming the entity, the table it looked for and the fix (`@Table`, or a migration), instead of a bare "SQL error"; on H2, a table created unquoted (stored in upper case) is reported with the two ways out.
* xref:usage.adoc#dependency-repositories[Repositories shipped in a library] — `vidocq:generate` runs Mansart's processor over a dependency jar's `@Repository` interfaces and their entities' metamodels, marks the jar so it is processed once, and vetoes another provider's generated implementation. A `@Find` whose parameters have no names in the class file binds each to the entity's only attribute of its type, or fails naming the method — before, the run-time path dropped such a parameter and returned every row.
* xref:reference.adoc#other-cdi-containers[Mansart on Weld and Open Liberty] — the jars run unchanged on other CDI containers, proven by two test modules: a generated repository and `@Transactional` on Weld SE, a repository on an Open Liberty data source. The Jakarta platform APIs are now `provided` (the container brings them), a generated repository is registered on a container that does not discover `@Singleton` classes, and `mansart-data-cdi` no longer opens its package to Vauban: a generated provider instantiates its producer.
* xref:usage.adoc#unresolved-methods[A method no query derives from fails the build] — the annotation processor reports it as an error instead of generating a method that throws at run time; `-Amansart.unresolvedMethods=warn` keeps the old behaviour.
* xref:usage.adoc#_derived_queries_by_method_name[The `Null` keyword] — `findByReturnedOnNull()`, the Jakarta Data 1.0 spelling, derives an `IS NULL` condition, as `IsNull` did.
* *A repository implemented at run time is announced* — when a repository is served by the run-time path (its generated implementation is missing, or the `java.lang.reflect.Proxy` fallback is used), Mansart says so at start-up. The run-time path also serves a generic repository contract and default methods, builds the model beside a metamodel Mansart did not generate, and serves a repository whose indexed implementation is gone; a nested or invalid repository no longer breaks the build.
* *Jakarta Data conformance fixes* — generated and run-time repositories are kept apart (MANSART-012); the `First` keyword is honoured in derived queries (MANSART-013); single-result methods throw `EmptyResultException` (MANSART-014); columns project to primitives and primitive arrays (MANSART-015); lifecycle methods take several entities (MANSART-016); `CrudRepository.insert`, `insertAll`, `update` and `updateAll` are implemented (MANSART-017); `@By` and `@OrderBy` are honoured on `@Find` (MANSART-018); `findFirst` without a match and `@Find` collections work on the run-time path (MANSART-019, MANSART-020); inserting an entity already stored is refused (MANSART-021); the entity of an inherited `@Find` method is resolved (MANSART-022); JDQL enum literals are resolved against the model, never by loading a class (MANSART-023); `Pagination.Keyset` cursors (MANSART-011) and recovered transaction `Xid`s (MANSART-010) compare by content.
* The runtime of a routed data store (`@Repository(dataStore = "...")`) belongs to its CDI container instead of a static cache: after a `vidocq dev` hot reload the repositories use the new container's data source rather than the previous one's closed data source, and the discarded layer can be collected (MANSART-041).

[#rc1]
== Brought by 0.4.0-RC1 (since 0.3.0)

=== 2026-10-11 — Persistence and Validation extraction

Persistence and the provisional Validation provider moved to
xref:noether::index.adoc[Noether]. They are no longer Mansart reactor modules.
Data, Pool and Transactions remain here with unchanged production semantics.
See xref:noether::migration.adoc[renamed artifacts, packages and providers].
Pre-extraction JPA entries below describe historical Mansart delivery.


=== Pool

* **The pool finds its driver with the application** — the JDBC driver is looked up through the application's class loader, then `DriverManager`, so a driver that only the application sees works; under Vidocq this used to fail with "No suitable driver" (mansart#42). xref:modules/mansart-pool.adoc#finding-the-driver[Finding the JDBC driver].

=== Jakarta Data

* **`@Param`, `@Find` and JDQL without `FROM` in compiled repositories** (mansart#41) — the annotation processor ignored `@Param` (a `:name` matched the Java parameter name only, so a jar needed `-parameters`), generated a `@Find` method that threw `UnsupportedOperationException`, and refused `@Query("WHERE …")` without `FROM`. It now honours all three, as the repositories generated at run time already did; its warnings name the type and the method, for a jar processed from class files. xref:usage.adoc#query-jdql[`@Query` JDQL].
* **An enum is stored as `@Enumerated` says** (mansart#26) — `@Enumerated` used to be read and then ignored: every enum was stored by its name, `@Enumerated(EnumType.ORDINAL)` included. Now `@Enumerated(EnumType.ORDINAL)`, and a bare `@Enumerated`, store the constant's index in an integer column, and `@Enumerated(EnumType.STRING)` stores its name, in writes, row mapping, projections, `WHERE` bindings and the generated DDL. An enum with **no** `@Enumerated` still stores its name, unlike the Jakarta Persistence default, which is the index. **This changes what an existing application does** if it declares `ORDINAL`: its tables hold names, and Mansart now writes and reads indexes for that attribute. Either switch the attribute to `@Enumerated(EnumType.STRING)` (or drop the annotation) to keep the data as it is, or convert the column to indexes before upgrading. xref:reference.adoc#enum-storage[Enum storage], xref:migration.adoc#upgrading-from-0-3-0[Upgrading from 0.3.0].
* **An `UPDATE` or a `DELETE` cannot follow a `SELECT` clause** — the JDQL parser Mansart uses at run time — for a repository generated at run time and for `JdqlExecutor.run` — read a `SELECT` clause and then went on to whatever followed it, so `SELECT this DELETE FROM Product` ran as a `DELETE`. Such a statement is now refused with a `MansartDataException`. A tool that tells reads from writes by the first keyword can no longer be led to run a write as a query. xref:usage.adoc#query-jdql[`@Query` JDQL].
* **`mansart-data-cdi` is an explicit bean archive** (mansart#33) — the jar now ships a `META-INF/beans.xml` (`annotated`), like `mansart-transactions-cdi`, so a CDI container that does not scan implicit archives, such as Weld SE by default, treats it as a bean archive. Under Vauban nothing changes. xref:reference.adoc#bean-archives[Bean archives].

=== The Jakarta Data core for tools

`io.vidocq.mansart.data.core` gives a tool — the Vidocq dev console, for one — what Mansart knows about an entity and a way to run a JDQL statement typed as text:

* **`EntityModels.of(Class<E>)`** — the model Mansart uses for an entity: its generated `_Entity.$MODEL`, or one built at run time from the mapping annotations. A tool no longer has to re-read the annotations or reflect on generated classes to describe an entity. xref:reference.adoc#tooling-api[The core API for tools].
* **`JdqlExecutor.run(jdql, parameters, model, runtime)`** — parses one statement against the entity's model, binds its named parameters by name, converts a text value to the attribute's type (enum, `java.time`, numbers, booleans, UUIDs), and runs it as a `@Query` method's statement would, returning a `JdqlResult`: entities, projected rows, a count or an aggregate's value. An overload with `maxRows` reads at most that many rows, as a SQL `LIMIT`. `isWrite` and `target` read a statement's first keyword and its entity without parsing it. xref:reference.adoc#tooling-api[The core API for tools].
* **An entity model no longer keeps its class loader reachable** — models used to be cached in a static map keyed by the entity class, which kept every class and its loader alive. Under a dev reload, where the application layer is replaced while Mansart stays, each discarded layer stayed in memory. Models now live with their class and go away with its loader. xref:reference.adoc#tooling-api[The core API for tools].

=== Jakarta Persistence

* **Noether JPA P0–P12 delivered within scope** — `noether-persistence` provides entity lifecycle, JPQL/Criteria, XML mapping, container integration, cache and Validation integration. The locally patched PostgreSQL TCK passes all non-skipped tests; comparative benchmarks and a modular Leyden AOT smoke are recorded. Remaining mapping boundaries and the local TCK patch are explicit; no formal certification or GraalVM native-image support is claimed. See xref:noether::index.adoc[implementation status], xref:tck.adoc[TCK evidence] and xref:performance.adoc[performance methodology].
