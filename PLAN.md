# Mansart — Global plan

## Vision

Three independent runtime sub-projects, designed to be used separately or together:

```
                    ┌──────────────────────────────┐
   user         →   │   mansart-jakarta-data       │   ← Jakarta Data 1.0 (repositories)
                    └──────────────┬───────────────┘
                                   │ can rely on
                                   ▼
                    ┌──────────────────────────────┐
                    │   mansart-persistence        │   ← Jakarta Persistence 3.2 (JPA)
                    └──────────────┬───────────────┘
                                   │ consumes
                                   ▼
                          ┌────────────────┐
                          │   DataSource   │   ← standard javax.sql
                          │   (your choice)   │      Hikari, Agroal, or…
                          └────────┬───────┘
                                   │
                                   ▼
                    ┌──────────────────────────────┐
                    │   mansart-pool               │   ← virtual-thread-native JDBC pool (optional, independent)
                    └──────────────────────────────┘

                          ┌────────────────┐
                          │   Dialect SPI   │   ← shared by data + persistence
                          └────────┬───────┘
                                   │
                          ┌────────┴────────┐
                          │                 │
                          ▼                 ▼
                       H2 (M3)        PostgreSQL (M4)
```

### Why three sub-projects

- `mansart-jakarta-data` is usable **without JPA** — direct JDBC backend, metamodel generated by APT, repositories compiled statically. Target: Vidocq applications that want the repository pattern without the weight of JPA.
- `mansart-persistence` brings JPA 3.2 when the user needs `EntityManager`, full lifecycle, second-level cache, or rich ORM mapping. When both modules are present, `mansart-jakarta-data` can delegate to `EntityManager` instead of pure JDBC.
- `mansart-pool` (optional) provides a **virtual-thread-native** JDBC `DataSource` and zero dependencies. No Maven dependency between the three sub-projects — `mansart-jakarta-data` does not care which pool the user passes it (Hikari, Agroal, Mansart Pool…).
- This separation reflects the Jakarta Data philosophy itself (one repository contract, multiple storage providers).

## Work order

1. **mansart-jakarta-data** (M2 → M6) — starts now.
2. **mansart-pool** (MP1 → MP4) — starts after Data M3 (need the H2 dialect to benchmark seriously). Independent — can be delivered on its own.
3. **mansart-persistence** (M7+) — will come after the Dialect SPI and Data TCK stabilize.

See `mansart-jakarta-data/PLAN.md` for the detailed plan of the first module.

## Key structural decisions (to validate)

1. **Reference backend for Jakarta Data: pure JDBC**, not JPA. Reason: avoid the circular dependency with `mansart-persistence`, keep a minimal binary, and demonstrate that Jakarta Data can be implemented without heavy ORM.
2. **Static repository generation** via APT. An annotated `@Repository` interface produces an `XxxRepositoryImpl` class at `compile`. No `java.lang.reflect.Proxy` proxy, no runtime weaving.
3. **Shared static metamodel**: APT produces `_Book`, `_Author`, etc., reusable by both modules (Data and Persistence) — same format as the JPA static metamodel for interop.
4. **Dialect = public SPI** loaded via `ServiceLoader` (`provides DialectFactory with …` in `module-info.java`). H2 and PostgreSQL first, MySQL/Oracle/SQL Server later. The SPI is shared by both modules.
5. **Connection pool = independent peer sub-project** (`mansart-pool`), not a dependency of `mansart-jakarta-data`. The user provides their `DataSource` (Hikari, Agroal, Mansart Pool…) to the Data runtime. Mansart Pool is virtual-thread-native, designed post-Loom (no pinning), zero-dep. See [`mansart-pool/PLAN.md`](./mansart-pool/PLAN.md).
6. **Jakarta Data 1.0 TCK outside the reactor** (standalone POM Model 4.0.0) — same ShrinkWrap constraint as the other Vidocq TCKs.

## Out of scope (explicit)

- Multi-tenancy.
- Second-level cache (belongs to JPA → `mansart-persistence` later).
- Schema migrations (Flyway/Liquibase to be integrated on the application side).
- NoSQL (Jakarta Data accepts other backends but that is not a Mansart goal).
- Reactive / R2DBC (Jakarta Data 1.0 is synchronous; Virtual Threads cover the need).
