# CLAUDE.md — mansart

Sub-project-specific guide. See also the workspace root `CLAUDE.md` for the cross-cutting philosophy.

## Mission

Provide the Vidocq ecosystem with three persistence building blocks, independent at runtime:

- `mansart-jakarta-data` — Jakarta Data 1.0 (declarative repositories). **Delivered — TCK 74/74 PASS.**
- `mansart-transactions` — Jakarta Transactions 2.0 (virtual-thread-native TM, `@Transactional`, `@TransactionScoped`). **Delivered — TCK smoke 5/5 PASS.**
- `mansart-pool` — virtual-thread-native JDBC pool, zero-dep, optional. **Delivered.**

`mansart-jakarta-data` renders its SQL through `mansart-data-dialect-spi`; Noether Persistence through its own SQL AST and dialects (`noether-jpa-dialect-*`, decision D4 in [Noether roadmap](https://codefloe.com/Vidocq/noether/src/branch/main/noether-persistence/ROADMAP.md)). `mansart-pool` is completely decoupled: it only provides a `javax.sql.DataSource` usable by any JDBC client.

## Prerequisites

- **Java 25** + **Maven 3.9.16** (`.sdkmanrc` coming in this folder).
- For TCKs: the Jakarta Data TCK resolves from Maven Central, and every pull request runs it (`ci.tck.command` in the root `pom.xml`). The full Jakarta Transactions suite is an Eclipse zip run with Ant (`mansart-transactions/install-tck.sh`), run by hand, never in CI.

## Architecture Constraints to Respect

1. **No runtime reflection** on entities or `@Repository` interfaces. Everything goes through APT (`mansart-data-processor`) which generates:
   - the static metamodel (`_Book`, `_Author`, …) with typed attributes;
   - an `XxxRepositoryImpl implements XxxRepository` implementation class per annotated `@Repository` interface.
2. **No runtime bytecode generation** (no ASM, no Byte Buddy, no dynamic proxy). If a case requires dynamic behavior, use the **Class-File API** (`java.lang.classfile`) — never ASM.
3. **Zero external dependencies** beyond `jakarta.data-api`, `jakarta.persistence-api`, `jakarta.transaction-api`, `jakarta.inject-api`, `jakarta.cdi-api`. JDBC is in the JDK. Drivers (`h2`, `postgresql`) stay in `<scope>provided</scope>` (the application provides them).
4. **Strict Java Modules** — each module has its `module-info.java`. The dialect SPI (`mansart-data-dialect-spi`) is `exports`; dialects (`mansart-data-dialect-h2`, `…-postgresql`) are `provides DialectFactory with …` and discovered by `ServiceLoader`.
5. **Virtual Threads** — all `PreparedStatement.execute*` calls run from a virtual thread. A JDBC connection must never be held across a `synchronized` block that wraps a blocking operation.

**Architecture rules as tests** — **ArchUnit** (`com.tngtech.archunit:archunit`, Apache-2.0, through the shared
`vidocq-archrules` library of `vidocq-parent`) is test scope, used only by the test-only module
`mansart-architecture-tests` (Vidocq/vidocq#289): its `ArchitectureRules` turn the constraints above into tests on
the shipped classes. The documented reflective fallbacks (the M7 runtime path, the lookups of generated code, the
optional JTA probe, the configured `XADataSource`, the interceptor's `Method`) are listed with their reasons in
`ArchitectureRules.REFLECTIVE_FALLBACKS`, and the transaction context's `ThreadLocal` in `THREAD_LOCAL_HOLDERS`; a
new one needs a documented reason there. Note: `RuntimeRepositoryProxy` (M7 runtime path, documented in `mansart-jakarta-data.adoc`) implements interfaces without a generated implementation with a Class-File API class; it has no `java.lang.reflect.Proxy` fallback.

## Delivered Modules

### mansart-jakarta-data sub-modules

| Sub-module | Role |
| --- | --- |
| `mansart-data-dialect-spi` | SPI: `Dialect`, `DialectFactory`, neutral query AST (sealed `Where`, `Attribute` hierarchy). |
| `mansart-data-dialect-h2` | H2 dialect (MERGE INTO, BIGINT GENERATED BY DEFAULT AS IDENTITY, native BOOLEAN). |
| `mansart-data-dialect-postgresql` | PostgreSQL dialect (INSERT … ON CONFLICT, RETURNING id). |
| `mansart-data-core` | Runtime: query plan execution, result-set ↔ entity mapping, connection management. |
| `mansart-data-processor` | APT (SourceVersion.RELEASE_25) — generates `_<Entity>` metamodel and `<Repo>Impl` classes. |
| `mansart-data-cdi` | CDI 4.1 Lite bootstrap (BCE) via Vauban. |
| `mansart-data-tests` | Unit tests (93/93 PASS) + Arquillian smoke tests (6/6 PASS). |
| `mansart-data-tck` | Jakarta Data 1.0 TCK runner — **OUT OF REACTOR** (standalone POM Model 4.0.0); **74/74 PASS** on H2 and PostgreSQL. |

Note: `mansart-data-api` was removed in M7-29 (redundant with `jakarta.persistence-api` — no separate re-export needed).

## Conventions

- PostgreSQL integration tests via **Testcontainers** in `<scope>test</scope>` only — never at runtime.
- Generated Data metamodel under `target/generated-sources/annotations/`: `_Entity` is the Data DSL convention.
  The JPA canonical metamodel `Entity_` belongs to the persistence provider's processor (Noether, Hibernate
  Processor): Mansart never writes it (Vidocq/noether#45, F15).
- All generated queries go through the `mansart-data-dialect-spi` AST — never inline SQL in `mansart-data-core`.
- Reproducible bugs → `BUG.md` (skill `/log-bug`). Performance measurements → `BENCH.md` (skill `/log-bench`).
- **Language** — commit messages, Javadoc, and all `.md` file content must be written in **English**.

## Documentation (Antora) conventions

The project documentation lives in `docs/en` as an Antora component and is
aggregated by the **vidocq-docs** site, which provides a **shared UI bundle** (banner,
logo, fonts, colours, footer). **Never customise the documentation UI per project** —
all visual harmonisation is centralised in `vidocq-docs/ui-bundle`.

### Gold reference
**Vauban** is the reference implementation for documentation structure. Mirror its
`docs/en` layout when creating or updating docs. **Chappe** (HTTP server)
and **Vidocq** (runtime orchestrator) are *special cases*, not references: they are not
Jakarta EE / MicroProfile spec implementations.

### Repository layout
- `docs/en/antora.yml` → `name: <project>`, `title:`, versioned per branch (`dev` prerelease on `main`, `'<version>'` on `docs/<version>`), `project-version` attribute, `nav:`, `lang: en`.
- Pages in `modules/ROOT/pages/`, navigation in `modules/ROOT/nav.adoc`, images in
  `modules/ROOT/images/`.
- **English-only** (ADR 0004 in vidocq-docs): no French mirror — do not reintroduce one.

### Canonical navigation (section order)
`index` → `getting-started` → `usage` → `concepts` → `internals` → `tck` →
`performance` → `reference` → `migration`

Multi-module projects (e.g. Vidocq, Mansart) may append `modules/*` / `sub-modules/*`
sub-pages after `migration`.

### TCK / Performance rule (not mutually exclusive)
- Every **spec implementation** — i.e. **all projects except Chappe and Vidocq** — MUST
  have a **`tck`** section documenting TCK coverage/status.
- Projects with a performance story (e.g. **Chappe**) keep their **`performance`** section.
- When **both** sections exist, order them **TCK first, then Performance**.
- **Chappe** and **Vidocq** do not require a `tck` section (not spec implementations).

### `index.adoc` structure
Follow Vauban's `index.adoc`: page title (`= <Project>`), `:description:`, a centred logo
(`image::<project>-logo.png[...,role=module-logo]`), a `[.lead]` paragraph, then
`== Origin of the name`, an `== At a glance` table, and ecosystem / quick-links sections.

### Logo
Provide `modules/ROOT/images/<project>-logo.png` (PNG), referenced from `index.adoc`.

## Build compatible extensions work at build only

A CDI build compatible extension works at build, and only there. `vidocq:generate` runs the extensions of an
application once and records what they did; the packaged application loads that record instead of running them
(Vidocq/vauban#288). An extension that breaks these rules loses work or checks in a packaged application:

- compute from the deployment's classes only: no configuration value, environment variable, outside file or network
  resource in a phase;
- check the start environment in an observer of `jakarta.enterprise.event.Startup` that throws a
  `DeploymentException`, fed with what the build collected (`withParam`); models: Ravel's `ConfigStartCheck`,
  Cervantes' `JwtConfigurationCheck`;
- add annotations, never remove them; carry data in parameters, never in fields of the extension;
- ask `ExtensionPhase.isBuildTime()` only as a last resort, in a class of its own: an extension that asks runs again
  at each start (Heisenberg's `InterceptorPriorityExtension`);
- the brick's Vidocq runtime extension adds its own beans with `VaubanContainerBuilder.addHostBean`, never
  `addBeanClass`, and its `-codegen` bundle brings the brick's CDI jar to the processor path;
- test both ways: the extensions run at start (TCK, another container) and frozen (the startup report says
  `cdi extensions  N extensions frozen at build`, and an invalid environment still stops the start).

Guide: `docs/writing-a-build-compatible-extension.md` in `Vidocq/vidocq-workspace`, and Vauban's concepts page,
"Writing an extension the build can freeze" (`docs/en/modules/ROOT/pages/concepts.adoc#writing-a-frozen-extension`).
