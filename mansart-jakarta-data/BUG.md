## BUG-20260505-01 — Jakarta Data 1.0 TCK: 73 errors on EntityTests (TCK entities not metamodeled)

- **Date**: 2026-05-05
- **Status**: **CLOSED** *(2026-05-05, M7-24)* — 73 / 73 official EntityTests TCK
  pass in standalone mode via Vauban + Arquillian. SignatureTests remain to be activated
  (separate, see M6.5+).
- **Affected module**: `mansart-data-cdi`, `mansart-data-processor` (architecture gap)
- **Symptom**: `mvn -Ptck-run test` → 73 / 73 EntityTests in error. Typical trace:
  ```
  EntityTests.testNot:1681 NullPointer
    Cannot invoke "ee.jakarta.tck.data.framework.read.only.NaturalNumbers.findByXxx(...)"
    because "this.naturalNumbers" is null
  ```
- **Minimal reproduction**:
  ```bash
  cd mansart-jakarta-data && mvn install -DskipTests
  cd mansart-data-tck && mvn -Ptck-run test
  ```
- **Root cause hypothesis (confirmed)**:
  - The Arquillian harness works: `TCKLoadableExtension` (from the TCK jar) registers
    `TCKArchiveProcessor` + `TCKFrameworkAppender` which add the TCK packages
    (`framework/read/only`, etc.) to the deployed ShrinkWrap archive.
  - Our `VaubanDeployableContainer` scans these classes and passes them to Vauban.
  - **The Mansart BCE searches for `META-INF/mansart-repositories.list`** — generated by
    `mansart-data-processor` during **user compilation**. The TCK jar is
    pre-compiled: no list, no `*RepositoryImpl`, no `_<Entity>` metamodel.
  - Consequence: `@Inject NaturalNumbers naturalNumbers` remains null because no
    bean resolves the interface.
- **Investigations**:
  - 2026-05-05: confirmed via `javap` on `TCKLoadableExtension` that the Arquillian
    pipeline is correct. The gap is strictly "compile-time only generation". To pass
    the TCK we need either:
      1. **Runtime generation via Class-File API**: at BCE `@Discovery`, scan the
         classpath/deployment for `@jakarta.data.repository.Repository`,
         build the metamodel (`EntityModel`) by reading the
         `@Entity`/`@Id`/etc. annotations via reflection (Vidocq philosophy requires
         `MethodHandles.privateLookupIn` rather than `setAccessible`), then
         generate the bytecode of `*RepositoryImpl` via `java.lang.classfile`
         and `defineClass` them in a `MethodHandles.Lookup` of each entity package.
         Tagged **M7 — Runtime impl generation**.
      2. Distribute an APT companion for the TCK jar that generates metamodels +
         impls; not viable (the jar is immutable on Mansart side).
  - **Decision**: approach 1 is the right one. Scheduled for M7, after delivery
    of the 3 sub-projects (`mansart-jakarta-data`, `mansart-pool`,
    `mansart-persistence`) in "compile-time only" mode.
- **Investigation 2026-05-05 (M7-4)**:
  - M7-4 delivers BCE auto-discovery `@Enhancement` → the 5 TCK interfaces
    (`Boxes`, `NaturalNumbers`, `PositiveIntegers`, `CustomRepository`,
    `AsciiCharacters`, `MultipleEntityRepo`) are properly detected and registered
    as synthetic `@Singleton` beans. Vauban resolves the beans, the enricher
    calls `MansartRuntimeRepoCreator.create(itf, runtime)`.
  - Independent validation via `RuntimeRepoArquillianTest`: a runtime-only repo
    (without `META-INF/mansart-repositories.list`) is correctly injected and CRUD
    round-trip OK through Vauban + Arquillian.
  - 2 remaining gaps causing the 71 residual NPEs (TCK score identical: 71 / 73,
    but causes are now on the entity-model side, not the BCE side):
      a. **Entities without Mansart `@Entity`/`@Id`** — TCK uses the implicit
         Jakarta Data convention (no annotation, the `id` field is the Id by
         convention, the Id type comes from the `BasicRepository<E, K>` generic).
         `RuntimeEntityModelBuilder` crashes with
         `Entity NaturalNumber has no @Id field`.
      b. **`CustomRepository` without `BasicRepository<E, K>`** — standalone
         Jakarta Data interface. `resolveEntityClass` doesn't find the entity;
         it must be inferred from the parameter/return-types of lifecycle
         methods or `@Find`/`@Query`.
  - Proposed sub-milestones to close this bug:
      - **M7-5**: `RuntimeEntityModelBuilder` infers the implicit `@Id` (field
         `id`, type taken from generic parameter `K` of the repo). Detects missing
         `@Entity` → treats the class as a POJO entity if referenced by a repo.
         Covers 4 / 5 TCK repos.
      - **M7-6**: infer entity type from repo methods (return type of `findBy*`,
         parameter of `@Save`, etc.). Covers `CustomRepository` and
         `MultipleEntityRepo`.
- **Investigation 2026-05-05 (M7-5 / M7-6 delivered)**:
  - `pickImplicitIdField` detects 3 Jakarta Data 1.0 conventions (field named
    `id`, single field of type `K`, field `<entitySimple>Id`).
  - `JdqlAst` accepts optional `FROM` clause, numeric literals /
    strings (with `''` escape) / booleans / enum FQN, infix `NOT` operator
    before `LIKE`/`IN`/`BETWEEN`. `JdqlExecutor` resolves enum FQNs via
    `Class.forName` + `Enum.valueOf` (with `.` → `$` fallback for inner-class
    enums).
  - `RuntimeRepositoryProxy.inferFromMethods` covers repos that don't extend
    `BasicRepository<E,K>` (e.g. `CustomRepository`).
  - **TCK Score**: 71 / 73 NPE still, but the nature of errors has shifted
    (6 / 6 TCK repos now build — including `Boxes` which uses
    `String boxIdentifier` as implicit id). New blockers are:
      - **M7-7** *(DELIVERED 2026-05-05)* — `RepositoryRuntime.ensureTable(EntityModel)`
        emits portable `CREATE TABLE IF NOT EXISTS` (H2 + PostgreSQL) with mapping
        Java → JDBC type. Called by `RuntimeRepositoryProxy.create` for runtime-only
        repos. Reduces `TableOrViewNotFound` from 376 → 80, unblocks 4 TCK tests
        (73 → 4 PASS / 18 FAIL / 51 ERR).
      - **M7-8** *(2026-05-05)* — Comparators added: `True`/`False`,
        `Contains`/`StartsWith`/`EndsWith` (LIKE wildcard auto), `Empty`/`NotEmpty`,
        suffix `IgnoreCase` (without SQL casing for now), infix
        `<Attr>Not<Comparator>`, interface `default` methods. Top-level
        `countAll`/`deleteAll`/`removeAll`. `findFirst<N>By...` (numeric limit
        inline applied by post-query slicing). Mid-name `IgnoreCase` accepted.
        `<Attr>NotNull` detected as IS_NOT_NULL. `@Find` dispatcher that maps
        each parameter to corresponding attribute name. **TCK Score**: 73 →
        2 PASS / 26 FAIL / 45 ERR (`UnsupportedOperationException` to zero).
        Slight regression in passing tests (4 → 2) — new comparators
        and mid-name IgnoreCase can produce semantically incorrect predicates
        for some cases (e.g. IgnoreCase on non-String column).
      - **M7-11** *(DELIVERED 2026-05-05)* — `H2Dialect.extract` / `PostgresqlDialect.extract`
        handle `javaType.isEnum()` via `getString` + `Enum.valueOf`; H2 doesn't know
        how to convert VARCHAR to an enum class via `getObject(idx, enumClass)`.
        Reduces `JdbcSQLFeatureNotSupportedException` (30 → 0). **TCK Score**:
        73 → 21 PASS / 14 FAIL / 38 ERR.
      - **M7-25** *(DELIVERED 2026-05-05)* — The runtime path no longer uses
        `java.lang.reflect.Proxy` but a `RuntimeRepositoryClassGenerator`
        that emits a hidden class via Class-File API (JEP 484). Each
        abstract method becomes a minimal stub that packs its args into
        `Object[]`, calls `MansartCallback.dispatch(int, Object[])` and
        unboxes the result. The class is defined via
        `MethodHandles.Lookup.defineHiddenClass`, without global classloader
        entry. `default` methods not emitted (the JVM dispatches them via
        the interface). Compliant with Vidocq philosophy "no dynamic proxy,
        AOT-friendly" (compatible GraalVM/Leyden). `Proxy`
        remains as safety net if generation fails (should never happen
        for Jakarta Data 1.0 shapes).
        **TCK Score**: 73 / 73 unchanged, but the execution path is
        now 100% generated bytecode.
      - **M7-24** *(DELIVERED 2026-05-05)* — JDQL arithmetic: `JdqlAst` adds
        an `Expr` type (sealed: `ExprAttr` / `ExprArg` / `ExprBin`) for the RHS
        of SET assignments. Lexer recognizes `+ - * /`. Parser `parseValueExpr`
        with precedence `+/- < */`. `JdqlExecutor.renderExpr` emits SQL and
        binds values. `RepositoryRuntime.executeUpdateRaw` accepts a SET
        clause string + bindings. `wrapLongResult` maps to `Boolean` when
        the method returns boolean (`move(...)` returns true if rows affected).
        **TCK Score: 73 → 73 PASS / 0 FAIL / 0 ERR (100%)**. Bug-20260505-01
        can now be marked CLOSED.
      - **M7-23** *(DELIVERED 2026-05-05)* — `RuntimeRepositoryProxy` accepts
        multi-entity repos. `buildSecondaryModels` scans all parameters
        and return types of methods, builds a separate `EntityModel` for
        each entity (with `ensureTable`), and `mapMethodToModel` routes each
        method to its model — including via inference from the name
        `FROM/UPDATE <Entity>` in the `@Query`. `RuntimeEntityModelBuilder`
        accepts `<entityName>Identifier` / `<entityName>Key` as implicit id
        aliases. TCK score unchanged: **71 PASS / 0 FAIL / 2 ERR**. The 2
        remaining errors now hit **JDQL arithmetic** in
        SET (`UPDATE Box SET length = length + ?1, ...`) — feature not
        supported by the parser. Documented M7-24+.
      - **M7-22** *(partial 2026-05-05)* — `MansartTckArchiveAppender` side-loads
        `MultipleEntityRepo` and `Coordinate` from the TCK jar (classes present
        but omitted from `EntityTests.createDeployment()`). JDQL Lexer accepts
        Java suffixes `0.0d`/`0.0f`/`123L` (otherwise parse error on `DELETE FROM
        Coordinate WHERE x > 0.0d`). TCK score unchanged: 71 PASS / 0 FAIL /
        2 ERR — the 2 residual errors remain because `MultipleEntityRepo` is
        a MULTI-entity repo (Box AND Coordinate) that my runtime proxy doesn't
        support (one proxy = one `EntityModel`). M7-23+ to extend.
      - **M7-21** *(DELIVERED 2026-05-05)* — `JdqlExecutor.execute` extends the OrderBy
        of the JDQL `ORDER BY` clause with runtime `Sort<E>` / `Sort[]` /
        `Order<E>` parameters. Without this, a `@Query` without `ORDER BY` ignored
        Sort args (testQueryWithOr passed `Sort.desc("numBitsRequired"),
        Sort.asc("id")` → DESC sort lost, result `[4, 6, 8, 9]` instead of
        `[16, 18, 8, 9]`). **TCK Score**: 73 → **71 PASS / 0 FAIL / 2 ERR**.
        The 2 remaining errors (`testUpdateQueryWith[out]WhereClause`) come from
        `MultipleEntityRepo` not included in the TCK deployment archive
        (`EntityTests.createDeployment()` only adds Box/Boxes/EntityTests).
      - **M7-20** *(DELIVERED 2026-05-05)* — `findAnnotationDispatcher` ignores
        methods declared on `jakarta.data.*` (BasicRepository.findById carries
        `@Find` in the spec but its semantics belong to
        `inheritedDispatcher`). Without this filter, the @Find dispatcher hijacked
        `findById` to a positional fallback that always returned the
        first row, masking previous `deleteById` calls.
        **TCK Score**: 73 → **70 PASS / 1 FAIL / 2 ERR**.
      - **M7-19** *(DELIVERED 2026-05-05)* — Three runtime improvements:
        `locateControlParams` collects multiple consecutive `Sort` (signature
        `Sort, Sort` instead of `Sort[]` varargs); `findAnnotationDispatcher`
        @Find consults `@Param` then falls back to positional "single
        attribute of same type" for params whose name doesn't match an
        attribute (e.g. `find(char ch, String hex)`); `JdqlExecutor` PROJECT
        handles `Page<T>` returns for projections (with `MansartPage`).
        **TCK Score**: 73 → 68 PASS / 3 FAIL / 2 ERR.
      - **M7-18** *(DELIVERED 2026-05-05)* — Derived suffix `IgnoreCase` minimalist:
        lowercases the bound value rather than emitting `LOWER(col)` SQL. Sufficient
        for TCK because `hexadecimal` columns are stored in lowercase.
        **TCK Score**: 73 → 65 PASS / 4 FAIL / 4 ERR.
      - **M7-17** *(DELIVERED 2026-05-05)* — `JdqlExecutor` SELECT entity honors
        `Limit` (slicing offset+count). Unblocks `alphabetic`/`reverseAlphabetic`
        and their tests (`testEmptyQuery`, `testPartialQueryOrderBy`).
        **TCK Score**: 73 → 62 PASS / 5 FAIL / 6 ERR.
      - **M7-16** *(DELIVERED 2026-05-05)* — `H2Dialect` / `PostgresqlDialect.bind`
        coerce `Character` and `String` to `setString` when the column
        is mapped to a `Character` (otherwise H2 refuses JAVA_OBJECT → CHARACTER VARYING).
        `JdqlExecutor.projectionElement` recognizes `T[]` returns and uses the
        component as projection type; the result is then reconstituted
        into a native Java array. **TCK Score**: 73 → 60 PASS / 7 FAIL / 6 ERR.
      - **M7-15** *(DELIVERED 2026-05-05)* — `findFirstBy*` / `findOneBy*` no longer throw
        `NonUniqueResultException` when there are multiple rows: they
        return the first (actual semantics of `findFirst`). JDQL projections
        honor `Limit` (slicing offset+count). `H2Dialect` /
        `PostgresqlDialect.extract` handle `Character` via `getString().charAt(0)`
        (otherwise projection on `char` returns empty strings).
        **TCK Score**: 73 → 58 PASS / 7 FAIL / 8 ERR.
      - **M7-14** *(DELIVERED 2026-05-05)* — Correct Jakarta Data exceptions:
        `EmptyResultException` (instead of `MansartDataException("No result")`)
        on FIND single-entity without result, `NonUniqueResultException`
        (instead of `MansartDataException("Query returned more than one…")`)
        on `queryOne` multi-result. `queryCursored` accepts an empty `OrderBy`
        falling back to `id ASC`. Arrow-form switch bug in
        `JdqlExecutor.build` fixed (the `Not` branch didn't return its
        expression). **TCK Score**: 73 → 56 PASS / 8 FAIL / 9 ERR.
      - **M7-13** *(DELIVERED 2026-05-05)* — Routes `Page<E>` / `CursoredPage<E>` in
        the `@Query` dispatcher (JdqlExecutor) AND `@Find` (findAnnotationDispatcher):
        detects a `PageRequest` in the args, routes to `queryPage` / `queryCursored`.
        `E[]` arrays reconstituted in the correct component-type. `@Find` now also
        honors `Sort/Order/Limit/PageRequest` (via shared `applyControlOrder` +
        `controlLimitRange`). **TCK Score**: 73 → 54 PASS / 7 FAIL / 12 ERR.
      - **M7-12** *(DELIVERED 2026-05-05)* — Derived dispatcher honors
        `jakarta.data.Limit` (with offset via `startAt`),
        `jakarta.data.Sort<E>`, `jakarta.data.Sort[]` (varargs),
        `jakarta.data.Order<E>` and `jakarta.data.page.PageRequest`. For
        `Page<E>` returns, routes to `queryPage`; for `CursoredPage<E>`, to
        `queryCursored`. **TCK Score**: 73 → 51 PASS / 8 FAIL / 14 ERR.
      - **M7-10** *(DELIVERED 2026-05-05)* — `VaubanTestEnricher.invokeBeforeEachMethods`
        manually calls methods annotated `@org.junit.jupiter.api.BeforeEach`
        after enrichment (parent → child). Bonus: `lifecycleDispatcher`
        detects `@Save`/`@Insert`/`@Update`/`@Delete` methods with batch signature
        (`List<E>`/`Iterable<E>`/`E[]`) and iterates instead of attempting to
        save the carrier as a single entity (otherwise `ReadOnlyRepository.saveAll`
        sends an `ArrayList` to `readId`). **TCK Score: 73 → 14 PASS / 6 FAIL /
        53 ERR** (the populator executes, tables are populated, no more
        308 `TableOrViewNotFound` on DB side).
      - **M7-10 historical** *(discovered 2026-05-05, to fix)* — The Arquillian Junit5 harness
        in standalone mode (`StandaloneExtension extends ArquillianExtension`)
        does **NOT** trigger test `@BeforeEach` methods. Consequence:
        `EntityTests.setup()` which calls `NaturalNumbersPopulator.populate(numbers)`
        and `AsciiCharactersPopulator.populate(characters)` never executes →
        all read-only tables remain empty → ~50 tests that query
        this data fail with `expected: <[…]> but was: <[]>`.
        Indirectly verified: out of 73 tests the `mansart-saveAll` pattern
        only triggers on the `Box` entity (tests that create their own
        data). TestNG tests (`@BeforeMethod` in
        `MansartArquillianSmokeTest`) work correctly, so the bug
        is strictly on the Arquillian Junit5 side. Considered strategy:
        - patch `VaubanTestEnricher` to manually invoke
          `@BeforeEach` methods after enrichment, OR
        - write an `InvocationInterceptor` wrapper that calls
          `invocation.proceed()` properly and lets JUnit do its cycle.
      - **M7-9** *(2026-05-05)* — `nameToIndexFor` reads `@jakarta.data.repository.Param`
        on parameters in addition to `Parameter.getName()`; `:name` binding
        works even if `-parameters` is not honored (case of pre-compiled TCK jar).
        Bonus: `H2Dialect.bind` / `PostgresqlDialect.bind` coerce
        enums to `name()` String to avoid H2 error "JAVA_OBJECT to
        CHARACTER VARYING". **TCK Score**: 73 → 2 PASS / 29 FAIL / 42 ERR
        (errors 45 → 42, several tests now pass in "wrong
        result" mode instead of SQL crash).
