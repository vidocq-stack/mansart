# HOW_TO_DEV_WITH_MISTRAL.md

How `mansart-jakarta-persistence` (Jakarta Persistence 3.2) is set up to be
implemented with **Mistral Vibe** — Mistral AI's CLI coding agent — on a
two-tier model split: **Mistral Medium 3.5** for reasoning, orchestration
and review; **Mistral Small 4** for mechanical, well-specified subtasks
(code edits, running a script and parsing its output, recording numbers).
Neither model is the one first proposed. The original ask was Devstral for
code and (later) Large 3 for reasoning; two dedicated research passes found
**Devstral deprecated and retired from Mistral's own cloud API**, and
**Large 3 shipped without a reasoning mode and isn't Mistral's agentic-work
model** (Medium 3.5 beats it by 21-29 points on the closest available
benchmarks). Both are explained in full, with sources, in §3 — read it
before assuming either model name means what its size implies.

This is the third documented attempt at this module, after
`feature/jakarteee-mansart-persistence-*` (Claude Code Max / an earlier
"vibe coding" pass) and `ybl/jpa-opencode` (a local model, Qwen3.6 on oMLX,
driven through OpenCode — documented in `PREPARE_OPENCODE.md` on that
branch). §8 below distills what that attempt got right and wrong, because
this setup exists specifically to not repeat the wrong parts.

**If you are here to use the setup rather than to understand it, go to
§11** — the operating manual. Sections 1–10 explain why each setting is
what it is, §12 lists what is confirmed vs. still unverified, and §14 is
how to reuse all of this (agents and generic skills, unchanged) on a
different sub-module or a different project entirely.

Everything here lives in the repository: `AGENTS.md` (at the mansart
root — generalized across every sub-module, see §2), `.vibe/config.toml`,
`.vibe/agents/`, `.vibe/skills/`. The pilot files
`mansart-jakarta-persistence/{PLAN,TASKS,STATUS}.md` are deliberately
**not** pre-written by this document — they're generated by Vibe itself,
on first use, via the `bootstrap-plan` skill (§7, §11.2). See §13 for the
full file manifest.

## 1. The tool

**Mistral Vibe** (PyPI package `mistral-vibe`, binary `vibe`) — a CLI
coding agent built by Mistral AI, confirmed two ways: by inspecting the
actual installed package on this machine (`uv tool install mistral-vibe`,
`~/.local/share/uv/tools/mistral-vibe`, version **2.24.2** at the time of
writing) *and* independently by a live web research pass. It is a real,
official Mistral product — not a colloquial name for something else —
announced **2025-12-09** alongside the Devstral 2 model family
(<https://mistral.ai/news/devstral-2-vibe-cli/>), upgraded to **Vibe 2.0**
on **2026-01-27** (<https://mistral.ai/news/mistral-vibe-2-0/>). Open
source, Apache 2.0, published under the `mistralai` GitHub org
(<https://github.com/mistralai/mistral-vibe>, ~4.9k stars at last check —
pin the tag matching the installed version, `main` may not match). It
ships its own authoritative self-documentation as a built-in skill
(`vibe/core/skills/builtins/vibe.py`) — cross-referenced throughout this
document, and the single best source of truth if this doc drifts from a
future version. Human-readable docs:
<https://docs.mistral.ai/vibe/code/overview>. "Vibe" is Mistral's umbrella
product brand (Vibe Chat / Vibe Work / **Vibe Code**, the CLI covered here)
— PyPI showed **2.24.5** during the research pass, one patch ahead of the
2.24.2 installed on this machine; run `vibe --check-upgrade`.

Install / update:

```bash
uv tool install mistral-vibe        # via uv (any OS) — what's on this machine
pip install mistral-vibe            # via pip
brew install mistral-vibe           # via Homebrew (macOS/Linux)
curl -LsSf https://mistral.ai/vibe/install.sh | bash   # one-line installer
vibe --check-upgrade                 # check now, prompt to install if newer
```

Vibe is **not** a fork of OpenCode or a similar existing harness — it is
Mistral's own implementation, with its own config format (TOML, not JSON),
its own directory conventions, and its own permission model. Concepts
carry over from the OpenCode setup (primary/subagent split, skills loaded
on demand, hooks, a `task` delegation tool with the same name) but the
exact mechanics differ in ways that mattered while writing this config —
see the corrections logged in §12.

## 2. Config layering and where things live

Vibe layers config from several sources, later layers winning:
defaults → **user** (`~/.vibe/config.toml`) → **project**
(`<root>/.vibe/config.toml`, only in a *trusted* folder — see below) →
environment (`VIBE_*`) → CLI flags → the active agent profile's own
overrides (applied last, when `--agent` selects a profile).

**Project discovery**: Vibe walks up from the current directory looking for
`.vibe/config.toml`, stopping at the trust boundary. For this project that
means running `vibe` from **`mansart/`** (or a descendant) — not from the
vidocq workspace root, and not from inside `mansart-jakarta-persistence/`
directly (agents/skills/tools directories are **not** searched recursively
into subdirectories — only at the discovered project root itself, confirmed
from `vibe/core/paths/_local_config_files.py`).

**Trust**: `mansart` is already listed in this machine's
`~/.vibe/trusted_folders.toml` — no trust prompt needed here. A fresh
machine gets prompted interactively on first `vibe` launch from `mansart/`,
or pass `--trust` for a one-off non-interactive run.

```
mansart/
  AGENTS.md               # committed — generalized engineering contract (§ below)
  .vibe/
    config.toml            # committed — providers, models, tool permissions
    agents/*.toml           # committed — dev + 7 subagents (§5)
    skills/*/SKILL.md        # committed — 5 skills incl. bootstrap-plan (§7)
  mansart-jakarta-persistence/
    PLAN.md TASKS.md STATUS.md   # NOT committed by this setup — generated by
                                   # Vibe itself via /bootstrap-plan (§11.2)
```

**AGENTS.md is native and hierarchical** — no wiring needed (OpenCode
required an explicit `instructions: [...]` array in `opencode.json`; Vibe
discovers `AGENTS.md` files by walking the directory tree). Confirmed from
`vibe/core/config/harness_files/_harness_manager.py`:

- `~/.vibe/AGENTS.md` (user-level; **not** `~/.vibe/instructions.md` — see
  §12, that file exists on this machine but is dead) loads at session
  start, plus every `AGENTS.md` from the project root up through the trust
  chain — outermost-first, closer-to-cwd wins.
- Files in **subdirectories** below the project root are injected
  **lazily**: the first time an agent reads a file below that root, Vibe
  walks up to the project root and injects any `AGENTS.md` it finds along
  the way. This project doesn't currently use that mechanism — see below.

**One `AGENTS.md`, at the mansart root, generalized across every
sub-module** — the setup started with a second, nested
`mansart-jakarta-persistence/AGENTS.md` carrying the persistence-specific
engineering contract (leaning on Vibe's lazy-subdirectory-injection
feature above), then consolidated back to a single root file once it
became clear the *rules themselves* (no runtime reflection, zero external
deps, strict Java modules, TDD, TCK-PASS-is-the-only-metric) are identical
across `mansart-jakarta-data`/`mansart-transactions`/`mansart-pool`/
`mansart-jakarta-persistence`, not persistence-specific — duplicating them
per sub-module would just mean editing N files every time one of them
changes. The root `AGENTS.md` now carries the general contract plus a
short "Current active work" pointer section naming whichever sub-module is
being worked on; update that pointer (and nothing else) when work moves to
a different sub-module. The lazy-nested-file mechanism above is still a
real Vibe feature — worth using again for a sub-module whose rules
genuinely diverge from the general contract, just not needed today.

## 3. The models — and a finding that changed the plan mid-way

Assigning a different model per agent is directly supported: each agent
profile (`.vibe/agents/*.toml`) can set its own `active_model`, `models`,
and even its own `providers` — confirmed both from the `AgentProfile`
dataclass (`vibe/core/agents/models.py`) and from Vibe's own shipped `lean`
builtin agent, which does exactly this (a domain-specific model, its own
provider, its own compaction model). The `task` tool then runs the target
subagent under *its* profile, model included. **Mechanically, any per-agent
model split works exactly as asked.** The two-tier split actually shipped
in this config — **Medium 3.5** for reasoning/orchestration, **Small 4**
for mechanical subtasks — is not the one first proposed (Devstral for
code, then Large 3 for reasoning); both substitutions are explained below,
each backed by a live research pass rather than the model-name naming
convention (bigger name ≠ more capable, twice now — see Devstral and Large
3 below).

### Mistral Medium 3.5

Released ~2026-04-28/30 (public preview), promoted to Vibe CLI's default
and Le Chat's default on **2026-05-22**
(<https://mistral.ai/news/vibe-remote-agents-mistral-medium-3-5>), General
Availability by the time of writing. Dense (not MoE), **128B parameters**,
**Modified MIT** open weights (`mistralai/Mistral-Medium-3.5-128B` on
Hugging Face), self-hostable on as few as 4 GPUs.

- API id: **`mistral-medium-3-5`** (also `mistral-medium-latest`; this
  project uses `mistral-vibe-cli-latest`, a third alias already live and
  proven on this machine — see the note below on why).
- Context: **256k tokens** (262,144, per the official model card,
  corroborated by OpenRouter and vals.ai).
- Max output tokens: **not published by Mistral on an owned page**; a
  third-party tracker (vals.ai) reports 80,000, sourced from the same model
  card but not independently confirmed there.
- Pricing (<https://docs.mistral.ai/inference/pricing>): **$1.50/M input,
  $7.50/M output, $0.15/M cached input** (90% off standard input — see the
  caching note below).
- Benchmarks Mistral publishes: **77.6% SWE-Bench Verified** (coding),
  **91.4% τ³-Telecom** (agentic tool-use). Described as Mistral's "first
  flagship merged model," unifying what used to be three separate models
  (Medium 3.1 for chat, Magistral for reasoning, **Devstral 2 for
  coding**) — reasoning depth is now a per-request parameter rather than a
  separate model.
- Function calling and structured/JSON outputs: both first-class,
  documented Features on the model card.
- No published needle-in-a-haystack / long-context degradation data — see
  §12.

**Why this project pins `mistral-vibe-cli-latest` rather than
`mistral-medium-3-5`/`mistral-medium-latest`**: it's the id already live
and populated with real, working pricing in this machine's
`~/.vibe/config.toml` (presumably set up by Vibe's own onboarding
specifically for CLI use) — the safer, proven choice over an alias not yet
exercised on this machine. All three should point at the same model.

### Devstral — deprecated, and retired from the cloud API

This is the finding that matters most for this document's stated goal.
**Devstral 2 and Devstral Small 2 are both marked "Deprecated" on
docs.mistral.ai** (5/22/2026 and 2/27/2026 respectively — the same day
Medium 3.5 launched) **and listed as RETIRED from La Plateforme**
(7/31/2026 and 3/31/2026), replacement in both cases: Mistral Medium 3.5.
Mistral's own launch blog for Medium 3.5 states it "replaces Devstral 2 in
our coding agent, Vibe CLI," and reports Medium 3.5 beating Devstral 2 on
SWE-Bench Verified (77.6% vs 72.2%). The Vibe CLI's own documented
"chat-capable models" table no longer lists any `devstral-*` id.

Devstral's release history, for completeness (all Apache 2.0 / Modified
MIT open weights except Devstral Medium, which was API-only):

| release | date | API id | params | context | SWE-Bench Verified |
| --- | --- | --- | --- | --- | --- |
| Devstral (Small) 1.0 | 2025-05-21 | `devstral-small-2505` | 24B | 128k | 46.8% |
| Devstral Small 1.1 | 2025-07-10 | `devstral-small-2507` | 24B | 128k | 53.6% |
| Devstral Medium 1.0 | 2025-07-10 | `devstral-medium-2507` | undisclosed | 128k | 61.6% |
| Devstral 2 | 2025-12-09 | `devstral-2512` | 123B dense | 256k | 72.2% |
| Devstral Small 2 | 2025-12-09 | `devstral-small-2512` | 24B | 256k | 68.0% |

**Confirmed twice now** (a second, independent research pass run when the
model assignment was revisited): every Devstral SKU is past its retirement
date on docs.mistral.ai's live deprecated-models table — Devstral Small
1.0 (retired 2025-11-30), Devstral Medium 1.0 and Devstral Small 1.1 (both
2026-05-31), Devstral Small 2 (2026-03-31), Devstral 2 (2026-07-31). Open
weights mean Devstral itself isn't going away even if the *hosted* endpoint
is; `devstral-local` (this machine's oMLX server, from the `ybl/jpa-
opencode` attempt) stays declared in `.vibe/config.toml` as a free
fallback. Nothing in this project defaults to cloud Devstral any more —
Small 4, below, does its job instead and is confirmed current.

### Mistral Small 4 — the model actually doing the "small tasks" work

Released **2026-03-16**, GA, **Apache 2.0** open weights, sparse
Mixture-of-Experts (128 experts, ~4-6 active/token depending on which of
Mistral's own two pages you read — a minor discrepancy between the launch
blog and the model card, both cited). It **absorbed both the old Devstral
(agentic coding) and Magistral (reasoning) lines** into one hybrid,
multimodal model — Mistral's own framing, not an inference.

- API id: **`mistral-small-latest`** (dated tag `mistral-small-2603`) —
  this project's alias is `mistral-small-4`.
- Context: **256k tokens**. No separate max-output figure published.
- Pricing: **$0.15/M input, $0.6/M output, $0.015/M cached input** — the
  cheapest of Mistral's three "flagship"-tier text models, ~10× cheaper
  than Medium 3.5 on output.
- Supports a `reasoning_effort` parameter (`none` for fast/instruct-style,
  `high` for deep reasoning) and native text+image input.
- **Mistral's own Vibe CLI documentation lists it for exactly this
  project's use case**: the CLI's "Providers and models" table row reads
  verbatim *"Mistral Small 4 | `mistral-small-latest` | Fast,
  cost-effective general use"* — sitting below Medium 3.5 ("(recommended)
  ... Flagship reasoning and code") in the same table.
- No SWE-Bench/tool-use/agentic benchmark numbers published by Mistral for
  Small 4 — a real gap, not an oversight on this document's part; only
  general-knowledge/instruction-following benchmarks (GPQA Diamond, MMLU
  Pro, Arena Hard, LiveCodeBench) appear in the launch materials.

`coder`, `tck-runner` and `tracker` (`.vibe/agents/*.toml`) default to
`mistral-small-4` — each file also carries the `devstral-local` and
`mistral-medium-3.5` alternatives, commented, in case a real card exposes
a quality gap Small 4 can't clear.

### Mistral Large 3 — considered for the reasoning role, and rejected

The natural reading of "Large" is "bigger than Medium" — Mistral's own
data says the opposite here, which is exactly why this got a dedicated
research pass rather than being wired in on the name alone.

Large 3 is real and current: released **2025-12-02**, status Active, no
retirement date, `mistral-large-latest` (dated `mistral-large-2512`)
**does** point at this current generation (the *previous* dated snapshot,
`mistral-large-2411` — "Large 2.1" — is the one that's deprecated
2026-02-27 → retiring 2026-05-31, replacement Mistral Medium 3.5). Sparse
MoE, 675B total / 41B active parameters, fully open **Apache 2.0** (more
open than Medium 3.5's "Modified MIT"), 256k context.

But on every axis that matters for this project's "planning, task
decomposition, hard reasoning" role, Mistral's own signals point away from
it:

- **Pricing is *lower* than Medium 3.5** — $0.5/M input, $1.5/M output,
  $0.05/M cached input (3-5× cheaper than Medium) — the opposite of what a
  "bigger, above-Medium tier" would cost.
- **It shipped without a reasoning mode.** The launch post says "a
  reasoning version is coming soon" — checked against Mistral's changelog
  through August 2026, it hadn't shipped as of the research behind this
  document.
- Mistral's own model catalog puts **Medium 3.5** in "Featured Models",
  branded "frontier-class... optimized for agentic and coding use cases";
  Large 3 sits in the general catalog, not featured, not branded agentic.
- **Third-party benchmarks confirm the gap in practice**: vals.ai ran both
  models live via the Mistral API and found Medium 3.5 ahead of Large 3 by
  **+29 points on the SWE-Bench-Verified subset** (64.7% vs 35.3%), **+21
  on Terminal-Bench 2.0** (30.3% vs 9.0%), and **+28 on Finance Agent**
  (46.1% vs 18.1%) — the three suites closest to "plan and execute a
  multi-step technical task." (One reversal: Case Law v2, -17 points for
  Medium, an irrelevant domain here.)
- Mistral's own deprecation-alternative guidance for retiring "Large"
  snapshots points existing users toward **Medium 3.5**, not Large 3.

**Conclusion**: Large 3 is a cheap, fully-open, general-purpose sibling
release — not a reasoning upgrade over Medium 3.5. `dev`, `thinker`,
`spec-reader`, `auditor` and `guardian` stay on Medium 3.5. Large 3 isn't
wired into this config at all; if a future card exposes a case where its
$0.5/$1.5 pricing is worth trying against Medium's judgment on a specific
task, add it as a third `[[models]]` alias the same way Small 4 was added,
and benchmark that specific task before trusting it more broadly.

### `thinking` level

`off | low | medium | high | max` (`vibe/config_values.py`).
`mistral-vibe-cli-latest` is set to `max` here (the shipped example in
Vibe's own doc uses `high`) — appropriate for an agent whose job is mostly
architectural decisions and review, not chat. Lower it if sessions feel
slow and decisions don't need the extra depth.

### Context window / `auto_compact_threshold`

Set to 150,000 for every model in `.vibe/config.toml`, below both Vibe's
own default (200,000, `DEFAULT_AUTO_COMPACT_THRESHOLD` in
`vibe/core/config/_defaults.py`) and Medium 3.5's actual 256k context — a
deliberate margin, not an oversight, in the spirit of the OpenCode setup's
"budget we choose to spend well" rather than the hard ceiling. Raise it
once a session's actual behavior near that threshold has been observed
once (see §6).

### Cost mechanisms worth knowing about (platform-wide, not project config)

- **Prompt caching** — 90% off cached input tokens, keyed by a
  `prompt_cache_key` Mistral's docs say is exactly suited to "agent
  completion requests that reuse the same context across turns." No config
  field for it was found in Vibe — presumably automatic. See
  `model-discipline`.
- **Batch API** — 50% off input+output for async/non-interactive work
  (queued, up to 24h) — not applicable to an interactive `vibe` session,
  but worth knowing about for a scripted bulk operation.
- **Regional inference** (EU vs. global endpoint) — +10% surcharge, not
  configured here.
- Rate limits (RPS / tokens-per-minute / tokens-per-month) are enforced but
  **no longer published as fixed numbers** — visible only in the
  authenticated Admin Panel (admin.mistral.ai/plateforme/limits). Exceeding
  one returns HTTP 429; monitor headroom via the `X-RateLimit-Remaining`
  response header if scripting anything at volume.

### Provider

`.vibe/config.toml` declares two providers: `mistral` (cloud,
`MISTRAL_API_KEY`) for every model actually used by default, and `omlx`
(local, `127.0.0.1:8000`) purely so `devstral-local` has somewhere to
resolve to once wanted — harmless if oMLX isn't running, since nothing
defaults to it. Set up the key:

```bash
vibe --setup            # interactive onboarding, sets MISTRAL_API_KEY
```

Or edit `~/.vibe/.env` directly (`MISTRAL_API_KEY=...`) — never ask an
agent to read or write that file; it is on Vibe's own hard-coded
do-not-touch list.

## 4. Tool permissions

`.vibe/config.toml`'s `[tools.bash]` block and each agent's own
`[tools.*]` overrides use **command-prefix matching**, confirmed by reading
`vibe/core/tools/builtins/bash.py`:

```python
def _matches_pattern(command: str, pattern: str) -> bool:
    return command == pattern or command.startswith(pattern + " ")
```

No globs, no trailing `*` — `"git status"` matches `git status` and
`git status --short`, never write `"git status*"`. A **denylist** match is
a hard `NEVER` (the command is refused outright, not confirmed); an
**allowlist** match is `ALWAYS` (auto-approved); anything unmatched falls
through to the tool's base `permission`.

Two different shapes are used on purpose, one per role:

- **`dev` (`.vibe/agents/dev.toml`) sets `permission = "always"` with a
  short `denylist`** (destructive git — `reset`/`clean`/`restore`/
  `checkout --`/`checkout HEAD`/`push` — plus `rm -rf` and
  `docker rm`/`docker volume rm`) — genuinely full-auto, not "ask for
  anything not on a curated allowlist." An earlier version of this file
  had `dev` inherit the project-level `ask` + safe-command-allowlist
  default instead, which meant every command outside that dozen-item list
  stalled on a prompt — contradicting "full-auto" everywhere this agent is
  described. The denylist is a **hard block**, not "ask": this agent's own
  workflow never legitimately needs those commands (a mistake gets fixed
  by another edit or a revert commit, not by discarding work or force-
  pushing), so there's no escape hatch to preserve — if one of those is
  ever genuinely needed, run it yourself, outside the session.
- **Every subagent (`coder`, `tck-runner`, `auditor`, `guardian`,
  `tracker`, `spec-reader`) keeps `permission = "ask"` with a narrow,
  curated allowlist** — appropriate for a scoped specialist, not a
  regression: `coder` doesn't need broad shell access to write code inside
  files it's told to touch, and the others are read-only reviewers by
  design.
- The **project-level** `.vibe/config.toml` `[tools.bash]` (`ask` +
  a safe-command allowlist) is the fallback for any *other* agent profile
  selected in a session (`ask`, `plan`, `accept-edits`, `auto-approve`) —
  none of those have their own bash block, so they inherit this one.

File tools (`read_file`, `grep`, `write_file`, `edit`) use a **different**
mechanism — path globs, checked in this order (from Vibe's own doc):
scratchpad → denylist → allowlist → sensitive patterns → outside-workdir →
base permission. `tracker`'s `.vibe/agents/tracker.toml` uses this to scope
it to exactly `STATUS.md`/`TASKS.md`.

### 4.1 Verify before trusting

This section was written from reading Vibe's source, **not** from
observing a real session. Two things to check on the first real run, the
same way the OpenCode setup verified its assumptions by capturing the raw
HTTP request (`PREPARE_OPENCODE.md` §4.1):

- Run any ordinary command (`mvn`, `git diff`, something not on `dev`'s
  denylist) as `dev` and confirm it just runs, no prompt.
- Confirm a denylisted command (`git push`, for instance) is **refused
  outright** as `dev` — not asked, refused, since `permission = "always"`
  + `denylist` means NEVER, not ask. If it prompts instead of refusing,
  or if it's silently allowed, the denylist entries aren't matching as
  expected — re-check the exact command Vibe receives (it may include a
  leading `cd ... &&` that changes what `command` is at match time), and
  recall this machine's **global** `~/.vibe/config.toml` sets
  `[tools.edit].permission = "always"` and `[tools.write_file].permission =
  "always"` for *every* project, not just this one — harmless for edits,
  but double-check it hasn't also loosened bash for a *different* agent
  profile than `dev`.

## 5. Agents

`.vibe/agents/*.toml`. One primary, seven subagents, plus Vibe's own
builtin `explore` (read-only codebase search — no custom file needed for
it). Consolidated from OpenCode's eleven-agent roster where the split no
longer earns its keep on a shared cloud model (see each file's own header
comment for what was merged and why).

| agent | type | model (default) | role |
| --- | --- | --- | --- |
| `dev` | primary | Medium 3.5 | lead developer; full-auto edits + bash (denylist only); delegates code-writing |
| `coder` | subagent | **Small 4** | implements a well-specified change |
| `spec-reader` | subagent | Medium 3.5 | read-only spec/TCK oracle; the only agent with `web_fetch` |
| `tck-runner` | subagent | **Small 4** | runs the TCK, reports real integers, never edits |
| `auditor` | subagent | Medium 3.5 | anti-drift review; read-only, reports only |
| `tracker` | subagent | **Small 4** | owns `STATUS.md`/`TASKS.md` only |
| `guardian` | subagent | Medium 3.5 | module-info + POM + virtual-threads review (merges 3 OpenCode agents); also the Sonar quality gate and security review (§ below) |
| `thinker` | subagent | Medium 3.5, `max` thinking | one hard decision, isolated context, after 2 failed attempts |
| `explore` | subagent (builtin) | inherits caller's | codebase search: `grep`, `read_file`, `skill` only |

Each `Small 4` agent's TOML also carries `devstral-local` (free, oMLX) and
`mistral-medium-3.5` (fallback) as commented `active_model` alternatives —
switch per agent if a real card exposes a quality gap (§3).

### The `task` tool — real delegation, structured, depth-limited to 1

Unlike OpenCode's `@name` convention (which turned out to be pure text —
typing `@auditor` in a prompt delegated nothing; only a command with
`agent:` + `subtask: true` actually forced a subagent), Vibe's `task` tool
is a real structured tool call (`agent`, `task` string) confirmed from
`vibe/core/tools/builtins/task.py`. Two hard constraints enforced by Vibe
itself, not by convention:

- Only a profile with `agent_type = "subagent"` can be a `task` target — a
  primary agent cannot be, and Vibe raises a clear error rather than
  silently falling back (as OpenCode's `--agent`-as-subagent path did).
- **Depth limit of 1**: a subagent cannot itself call `task`. Keep work
  handed to `coder`/`spec-reader`/etc. self-contained — they cannot
  delegate a sub-task further.

`dev`'s `[tools.task].allowlist` pre-approves all seven custom
subagents plus `explore`, so a session doesn't stall on a permission
prompt for every delegation.

### Agent TOML schema (from `vibe/core/agents/models.py`)

`display_name`, `description`, `safety`
(`safe|neutral|destructive|yolo`), `agent_type` (`agent|subagent`),
`install_required` are metadata; **everything else in the file is a raw
override merged into the full config for that agent's session** —
`active_model`, `models`, `providers`, `compaction_model`, `tools.*`,
`enabled_tools`/`disabled_tools`, `bypass_tool_permissions`,
`system_prompt_id`. `system_prompt_id` **replaces** Vibe's built-in system
prompt outright (the same trap the OpenCode doc found: a custom agent's
prompt doesn't append to the harness default, it substitutes for it) — none
of our agents set it, deliberately: they inherit the built-in `cli`
scaffolding and layer `AGENTS.md` + skills on top, which is additive.
Vibe's own `explore`/`lean` builtins **do** swap it, appropriately, for
narrow enough personas that the full interactive scaffolding is dead
weight — worth trying on `tracker`/`tck-runner` (`system_prompt_id =
"minimal"`, a built-in Vibe ships for exactly this) as a follow-up
optimization once the setup is proven, not before.

## 6. Compaction has no off switch

The OpenCode setup ran with `compaction.auto: false` after measuring that
compaction collapsed a 3B-active local model's tool-call rate from 98% to
0% over four turns (`PREPARE_OPENCODE.md` §"Why auto-compaction is OFF").
Vibe has no equivalent boolean — compaction always fires once
`auto_compact_threshold` is reached (confirmed from
`vibe/core/agent_loop/_loop.py:_run_compaction`); only the threshold and
the model used to summarize (`compaction_model`) are configurable. **This
project's config uses Small 4 as the compaction model** — confirmed GA
(§3), so a compaction that fires won't hit a retired endpoint (that would
hard-error, not degrade), and it's exactly the mechanical summarization
task Small 4 is positioned for, cheaper than spending Medium's budget on it.

Whether Medium 3.5 / Small 4 degrade the same way OpenCode's local model
did after a compaction is **not measured on this setup** — treat the first
real compaction as an experiment (see the `model-discipline` skill for what
to watch for). For anything scripted/unattended, Vibe's own
`--max-tokens`/`--max-turns`/`--max-price` flags on `vibe -p` are a native
hard stop OpenCode never had — use them.

## 7. Skills

`.vibe/skills/<name>/SKILL.md` — Markdown with YAML frontmatter
(`name`, `description`, optional `allowed-tools`, `user-invocable`),
loaded on demand via the `skill` tool, exactly the same file-per-directory
convention as OpenCode. Only the frontmatter sits in the always-on system
prompt; the body is fetched when an agent decides it's relevant.

- **`mansart-jpa`** *(project-specific)* — reactor layout, build commands,
  pointer to `vidocq-quality` for Sonar.
- **`mansart-jpa-tck`** *(project-specific)* — TCK scale, the out-of-reactor
  runner, the official-DDL schema trap.
- **`vidocq-codegen`** *(generic, §14)* — the three-tier static codegen
  doctrine, in full.
- **`vidocq-quality`** *(generic, §14)* — the SonarQube-on-Docker mechanism
  shared by every mansart sub-project (container, port, the
  `-Pquality`/`verify` gotcha, reading the gate via API) plus what counts
  as a security review (Sonar vulnerabilities/hotspots on new code,
  known-vulnerable dependencies — see `guardian`'s expanded role in §5).
- **`model-discipline`** *(generic, §14)* — cost table, the compaction
  caveat above, the write-size rule, delegation triggers.
- **`bootstrap-plan`** *(generic, §14)* — the only **user-invocable** one (`/bootstrap-plan`
  in a session, or typed as the user's own message — see §11.2): generates
  a sub-module's `PLAN.md`/`TASKS.md`/`STATUS.md` from scratch, generalized
  across sub-modules rather than hardcoded to persistence. Confirmed
  mechanism: a `SKILL.md` with `user-invocable: true` appears in the `/`
  autocompletion menu — this is how Vibe implements what OpenCode called a
  custom slash command.

## 8. What the previous (local-model) attempt got wrong — and the fix here

`ybl/jpa-opencode` (Qwen3.6-35B-A3B on oMLX, driven by OpenCode) reached
**79/95 planned cards (83%) across M0–M4** — real unit-test coverage, 315
passing tests in `mansart-persistence-core` — while the **official TCK
provider was never actually wired to a real implementation**: the last
measured run shows `991 run, 989 errors, 2 skipped`, *unchanged from the
M0 baseline*, all failing at `PMClientBase.setup()` because the TCK's
persistence unit still points at a stub. A milestone (`M1`, "metadata: APT
+ runtime Metamodel") was marked `DONE` with a card (`JP-20`) whose own
"proof" line claims *"257 methods PASS"* while its own "notes" line, in the
same entry, says *"TCK 991 run, 989 errors... same baseline"* — a direct
self-contradiction that a fresh session reading only `STATUS.md`/`TASKS.md`
would not catch.

Two concrete fixes, both baked into the tools that generate and enforce
the plan now rather than into a pre-written `TASKS.md`:

1. **The `bootstrap-plan` skill's own instructions require M0 (or
   whichever milestone is first) to end with a real, wired
   `PersistenceProvider` and a measured non-baseline TCK number before any
   metadata/CRUD milestone starts** — it states this exact prior failure
   as the reason, by name, so a future planning session can't quietly drop
   the constraint. `AGENTS.md`'s engineering contract adds the general
   version of the same rule: "the only real progress metric... is the
   official TCK PASS/total... never a number one agent reports about its
   own work without another agent independently measuring it."
2. **`tracker` (which writes `STATUS.md`/`TASKS.md`) and the number it
   records come from `tck-runner`'s measured output, not from `dev`'s
   own summary of what it did.** The two roles are separate subagents for
   exactly this reason — mirrors the OpenCode design intent, but the
   OpenCode session apparently didn't enforce it in practice for JP-20.

The rest of what worked in the OpenCode attempt carries over unchanged:
small cards (≤4 files, one proving test), one card per session, delegate to
burn a subagent's context instead of the primary's, never let a raw build
log into the window, keep a single `write` under ~150 lines.




That's the whole prompt: the skill (`.vibe/skills/bootstrap-plan/SKILL.md`)
carries the full instructions (§7) — it reads `AGENTS.md` (self-contained,
**deliberately never `CLAUDE.md`** — see that file's own header) + the
`mansart-jpa`/`mansart-jpa-tck` skills + `mansart-jakarta-data` as

first milestone's cards, and delegates the actual `TASKS.md`/`STATUS.md`
write to `tracker`. It also accepts an explicit target:
`/bootstrap-plan <directory> <spec>` bootstraps a different or brand-new
sub-module without needing anything about it to already be written down
anywhere — say what it is and where it lives, in the command itself. If
Vibe hasn't indexed the new skill file yet (e.g. it was added after the
session started), run `/reload` first, or paste the skill's own body as
the prompt directly — it's self-contained and doesn't
require the slash form to work. Review what got written before starting
the first real card; a plan is a draft, not a contract.

### 11.2 A session

```bash
cd ~/projects/perso/vidocq/mansart
vibe                     # default_agent = dev, set in .vibe/config.toml
# or explicitly:
vibe --agent dev
```

Then, inside the session, follow the protocol in the root `AGENTS.md`
(auto-loaded): read `STATUS.md`, pick exactly one `TODO` card from
`TASKS.md`, state the failing test before writing anything, TDD loop,
delegate code-writing to `coder`, validate (build + unit + `auditor` +
`tck-runner` if the card names a TCK client), delegate the write-up to
`tracker`, commit. **One card per session** — quit and relaunch for the
next one. If `STATUS.md`/`TASKS.md` don't exist yet, that's what
`/bootstrap-plan` (§11.1) is for — `AGENTS.md` says so explicitly, so a
session that starts without them should reach for it rather than
improvising a plan inline.

### 11.3 Mid-session cheatsheet

| you need | delegate to |
| --- | --- |
| what the spec/TCK says | `spec-reader` |
| where something already exists | `explore` |
| one TCK client's real numbers | `tck-runner` |
| is this card really done | `auditor`, then check the numbers yourself |
| a `module-info.java`/`pom.xml`/concurrency question | `guardian` |
| stuck twice on the same problem | `thinker` |
| the actual code for a well-specified change | `coder` |
| `PLAN.md`/`TASKS.md`/`STATUS.md` missing or need regenerating | `/bootstrap-plan` (§11.1) |

### 11.4 Non-interactive / scripted runs

```bash
vibe -p "..." --agent dev --max-tokens 200000 --max-price 5 --auto-approve
```

Native session-level hard stops (`--max-turns`, `--max-price`,
`--max-tokens`) — no equivalent existed in the OpenCode setup. Use them for
anything unattended.

## 12. What is confirmed vs. still unverified

Confirmed **two ways** — reading the installed v2.24.2 source directly,
*and* independently by a live web research pass that agreed with it —
during the writing of this document:

- **Devstral is deprecated and retired from La Plateforme** (§3) —
  confirmed by two independent research passes now, agreeing on the exact
  retirement dates per SKU; already reflected in every agent file and in
  `.vibe/config.toml`. No agent references cloud Devstral any more.
- **Mistral Small 4 is GA and current** (§3), confirmed live against
  docs.mistral.ai and against Vibe CLI's own model table, which recommends
  it by name for "fast, cost-effective general use" — the model actually
  running `coder`/`tck-runner`/`tracker`/`compaction_model` now.
- **Mistral Large 3 shipped without a reasoning mode and isn't Mistral's
  agentic-work model** (§3) — deliberately not used for the reasoning/
  planning role despite the naming intuition; Medium 3.5 measurably
  outperforms it on the closest available benchmarks (vals.ai, +21 to +29
  points on SWE-Bench-Verified/Terminal-Bench/Finance-Agent).
- **Vibe rewrites `.vibe/config.toml` on its own and strips comments when
  it does.** Observed directly on this project: after the first real
  `vibe` launch, `config.toml` came back with `applied_migrations =
  ["bash_read_only_defaults_v1"]` added, `[tools.bash].allowlist` merged
  with Vibe's own built-in read-only defaults and re-sorted alphabetically
  — confirming the allowlist genuinely merges across layers rather than
  being replaced (previously only inferred from source) — and every
  explanatory `#` comment in the file gone. Re-add documentation as a
  comment expecting it to survive the next Vibe-triggered rewrite; it
  won't. `.vibe/agents/*.toml` were not touched by this.
- **No Java LSP integration exists in Vibe.** Confirmed absent both from
  reading the installed package's source (no LSP/jdtls/tree-sitter-as-
  navigation-tool code anywhere) and from an explicit search of the public
  README/docs/AGENTS.md that returned nothing. Code search is `grep` (with
  ripgrep support) plus plain file reads — not AST/symbol-aware. A
  `tree-sitter`/`tree-sitter-bash` dependency does exist internally, but
  backs the bash-tool's command-safety parsing (§4), not user-facing code
  navigation. Until a real MCP LSP bridge is wired in via `[[mcp_servers]]`
  and confirmed working, agents navigate Java with `grep`/`read_file`
  only — see `model-discipline`. (A stale `~/.vibe/mcp.json` entry on this
  machine, `"java-lsp"` → `@modelcontextprotocol/server-lsp`, is dead
  regardless — Vibe does not read `mcp.json` at all; MCP servers belong in
  `[[mcp_servers]]` inside `config.toml`, or `vibe mcp add`.)
- **The `[tools.bash]` field names are `allowlist`/`denylist`** (verified
  by reading `BashToolConfig` in the installed source) — the public
  README's own inline example instead shows `allow = [...]` / `deny =
  [...]`. Trust the source-verified names used throughout this project's
  config; if a future Vibe version renames the fields, `/config`'s field
  browser will show the real name in use.

Still genuinely open:

- **Bash allowlist matching in practice** (§4.1) — read from source, not
  yet observed on a live command.
- **`auto_compact_threshold = 150000`** (§3) — set with headroom below
  Medium 3.5's confirmed 256k context, but not yet observed against real

- **Compaction behavior on Medium 3.5** (§6) — unmeasured; the OpenCode
  finding (narration collapse after compaction) is specific to a heavily-

- **Codestral** (`codestral-latest`) as a possible third option for

## 14. Porting this method to another project

The whole point of the renaming and de-JPA-ing done in this section: this
setup is meant to be **moved**, not re-derived, for the next mansart
sub-module (`mansart-transactions`, `mansart-pool`) or any other project
that wants the same TDD/TCK/zero-reflection/Sonar discipline — inside this
workspace or outside it.

### What's already portable, unchanged

- `.vibe/agents/{dev,coder,spec-reader,tck-runner,auditor,tracker,
  guardian,thinker}.toml` — no spec, sub-module, or project name in any of
  them. Copy the whole `.vibe/agents/` directory.
- `.vibe/skills/{bootstrap-plan,model-discipline,vidocq-quality}/SKILL.md`
  — same.
- `.vibe/config.toml`'s providers/models/`[tools.bash]`/`[tools.web_fetch]`
  structure — copy it too; only the two `vidocq-sonar` bash-allowlist
  lines are workspace-specific (drop them outside this workspace, keep
  them for another mansart/Vidocq sub-project).

### What genuinely can't be generic, and why

One thing, and it's supposed to be specific: **a project-architecture
skill** (`mansart-jpa` is this project's). It answers "what are we
actually building" — the reactor layout, which components are shared with
which sibling module, the build commands, the Sonar `projectKey`. That
content *is* the project-specific information; genericizing it away would
just mean re-deriving it from scratch every session instead of writing it
down once. If the target has an official TCK, it also needs a sibling
`*-tck` skill (`mansart-jpa-tck`'s shape: artifact coordinates, test
count, schema/DDL traps) — the TCK mechanics differ enough between specs
(different artifact, different schema source, different known traps) that
a generic version would be too vague to save any real work.

Root `AGENTS.md`'s **"Current active work" section** is the other
necessarily-specific piece, but it stays small on purpose: mission
statement, locked decisions, which skills to load, which prior branches
are out of scope. Everything *policy-shaped* (TDD, zero reflection, TCK
PASS as the only metric, Sonar+security gate, English, Java 25) stays in
the general "Engineering contract" above it and never needs touching.

### The actual steps

1. Copy `.vibe/agents/` and `.vibe/skills/{bootstrap-plan,model-discipline,
   vidocq-quality}/` into the target project's `.vibe/`.
2. In the target's `AGENTS.md` (create one at its root if it doesn't have
   one; add a "Current active work" section if it does but covers
   something else), write: the mission and spec, the locked design
   decisions, and which skill(s) to load — mirror this project's
   "Current active work" section above as the template.
3. Write one project-architecture skill for the target, mirroring
   `mansart-jpa`'s shape (reactor layout, what's shared with which
   sibling, build commands, `projectKey`) — and a `*-tck` skill too if
   there's an official TCK, mirroring `mansart-jpa-tck`.
4. Run `/bootstrap-plan [directory] [spec]` (§11.1) — it takes the target
   and spec as explicit arguments precisely so this step doesn't need
   anything pre-written about the new target beyond what step 2/3 just
   wrote.

This project's own bootstrap (`mansart-jakarta-persistence`, done via
steps 2–4 above before this document was fully written) is the worked
example — read its `AGENTS.md` section and `mansart-jpa`/`mansart-jpa-tck`
skills as the template rather than starting from a blank page.
